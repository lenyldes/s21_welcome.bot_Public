## Что это такое?

Автоматизированный сервис безопасного онбординга и строгой верификации участников основного обучения Школы 21 в закрытое Telegram-сообщество. Система исключает человеческий фактор и предотвращает имперсонацию с помощью двухфакторного подтверждения личности через закрытый корпоративный контур Rocket.Chat.

> 🚀 **Личный Daily Driver:** \
> В проде с мая 2025 года. Более 400 пользователей!

## Зачем нужен этот проект

При запуске нового учебного потока в Школе 21 каждый раз возникает необходимость централизованно добавлять сотни студентов («пиров») в закрытый чат кампуса. 

Обычные подходы не обеспечивали должного уровня безопасности:
- **Публичные инвайт-ссылки:** быстро утекают в сторонние чаты и каналы, делая сообщество уязвимым для спама и нежелательных участников.
- **Проверка по нику в Telegram:** логины студентов в интранете открыты для всех учащихся кампуса. Любой участник мог назваться чужим логином, а Telegram-юзернейм никак не привязан к корпоративной учетной записи.
- **Ручная модерация:** проверка сотен заявок вручную парализует работу администраторов и неизбежно приводит к ошибкам из-за человеческого фактора.
- **Изоляция от сотрудников:** требовалось гарантировать, что в студенческий чат не попадут администраторы и сотрудники школы. Это необходимо, чтобы сохранить атмосферу неформального и доверительного общения между пирами.

Так появился `s21_welcome.bot` — инструмент с архитектурой **Out-of-band 2FA**, использующий корпоративный мессенджер школы как доверенный Identity Provider. Проект стал практическим полигоном для отработки DevOps/SRE-навыков: от безопасного управления конфигурацией и секретами до контейнеризации, демонизации через systemd, структурированного логирования и разработки инструментов аварийного восстановления данных.

### Сравнение: Способы онбординга в закрытое комьюнити

| Критерий | Ручная модерация | Ссылка по открытому нику | s21_welcome.bot (Out-of-band 2FA) |
| :--- | :--- | :--- | :--- |
| **Защита от имперсонации (спуфинга)** | Низкая (человеческий фактор) | Отсутствует (ник легко скопировать) | **Абсолютная (OTP доставляется в ЛС интранета)** |
| **Автоматическая фильтрация стаффа** | Зависит от бдительности админа | Отсутствует | **Автоматическая (WhiteList + Staff Detection)** |
| **Скорость онбординга одного пира** | От часов до суток | ~10 секунд | **Менее 1 минуты (self-service)** |
| **Защита ссылки от пересылки** | Нет (ссылка многоразовая) | Нет (ссылка многоразовая) | **Одноразовый инвайт (1 переход, TTL 24 часа)** |
| **Аудит и прослеживаемость** | Ручные таблицы / блокнот | Отсутствует | **Полная связка в SQLite: `TG_ID <-> School_Login <-> Invite`** |

## Стек технологий

- **Ядро сервиса:** Python 3, pyTelegramBotAPI (`telebot`), Requests.
- **Внешние интеграции:** Rocket.Chat REST API (`im.create`, `chat.postMessage`) для защищенной доставки одноразовых кодов через закрытый корпоративный контур кампуса.
- **Хранение данных и состояний:** SQLite3 (доменная изоляция таблиц: FSM состояний диалога, белый список пиров, временные OTP-сессии, реестр выданных инвайтов).
- **Инфраструктура и оркестрация:** Docker, Docker Compose, Linux systemd (process supervision, автоперезапуск, интеграция со службой syslog).
- **Надежность и SRE-инструменты:** `TimedRotatingFileHandler` (суточная ротация файлов логов без потери истории), утилита анализа логов и аварийного восстановления целостности данных (`scripts/fix.py`).

## Быстрый запуск

### Требования

- Docker Engine 20.10+ и Docker Compose v2+ **ИЛИ** Python 3.10+ с установленным `venv`
- Токен Telegram-бота (от `@BotFather`)
- Учетная запись администратора/бота в корпоративном Rocket.Chat (Personal Access Token)

### Установка и старт через Docker Compose

1. **Клонируйте репозиторий:**
   ```bash
   git clone https://github.com/lenyldes/s21_welcome.bot_Public.git
   cd s21_welcome.bot_Public
   ```

2. **Настройте переменные окружения:**
   ```bash
   cp .env.example .env
   # Укажите реальные токены и параметры чата в .env
   ```

3. **Запустите контейнер:**
   ```bash
   docker compose up -d --build
   ```

4. **Проверьте статус сервиса:**
   ```bash
   docker compose logs -f
   ```

### Альтернативный запуск через Linux systemd

Для работы сервиса непосредственно в ОС хоста подготовлен готовый systemd unit:
```bash
# 1. Создание виртуального окружения и установка зависимостей
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

# 2. Установка и запуск сервиса
sudo cp deploy/systemd/telegram-welcome.bot.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now telegram-welcome.bot
```

## Ключевые инженерные решения

1. **Out-of-Band двухфакторная аутентификация через закрытый интранет:**  
   Вместо ненадежной валидации по открытым данным бот использует Rocket.Chat как доверенный Identity Provider. Так как учетные записи в Rocket.Chat привязаны к корпоративному SSO/LDAP школы, получение кода в ЛС однозначно подтверждает, что запрос на добавление исходит от реального владельца студенческого логина.

2. **Zero Trust генерация динамических одноразовых инвайтов:**  
   Сервис не использует и не хранит статические ссылки на сообщество. При успешной аутентификации Telegram API генерирует уникальную ссылку с жесткими ограничениями: `member_limit=1` (одноразовое использование) и `expire_date = now + 24h`. Это исключает распространение ссылок третьим лицам.

3. **Доменное разделение SQLite хранилищ:**  
   Вместо единой монолитной БД с рисками блокировок при конкурентной записи (`sqlite3.OperationalError: database is locked`), данные разнесены по отдельным файловым базам:
   - `white_list.db` — справочник допущенных логинов кампуса;
   - `user_state.db` — персистентный FSM (состояния диалога);
   - `verification_code.db` — активные OTP-коды и жизненный цикл сессий;
   - `usernames_to_user_id.db` — сквозной маппинг платформенных и Telegram-аккаунтов;
   - `is_used_link_*.db` — идемпотентность и защита от повторных запросов.

4. **Инфраструктурная надежность и Disaster Recovery (SRE-подход):**  
   - **Process Supervision:** запуск под управлением systemd / Docker с политикой `restart: unless-stopped` гарантирует восстановление после падений.
   - **Бесперебойное логирование:** `TimedRotatingFileHandler` ежедневно ротирует логи в полночь, обеспечивая полную историю действий.
   - **Аварийное восстановление (`scripts/fix.py`):** утилита автоматического парсинга ротированных логов позволяет реконструировать таблицы связок и выданных ссылок при повреждении файлов баз данных.

## Практика разработки и особенности процесса

Проект создавался в боевых условиях сжатых сроков непосредственно перед стартом первой волны обучения. Разработка прошла эволюционный путь (версии 1.0 -> 2.0 -> 3.0) с живой отладкой в продакшне под реальной нагрузкой в сотни одновременных запросов:

- **1.0: Переход к персистентному FSM:**  
  В первой версии состояния пользователей хранились в оперативной памяти (in-memory словари). Первый же плановый перезапуск сервиса привел к сбросу сессий пиров, находящихся на шаге ввода кода. Решением стал перевод FSM в дисковую SQLite базу (`user_state.db`), что сделало процесс верификации устойчивым к рестартам.

- **2.0: Устранение коллизий параллельных запросов:**  
  Наплыв сотен студентов в первые часы старта выявил проблемы конкурентного доступа к единому файлу БД. Архитектура была декомпозирована на узкоспециализированные базы данных, работающие независимо.

- **3.0: Трассировка и утилиты восстановления:**  
  Сложные краевые случаи (смена Telegram-юзернейма пользователем во время верификации, сбои внешнего API Rocket.Chat) потребовали внедрения сквозного логирования и создания скрипта `scripts/fix.py` для аудита и синхронизации данных.

## Тестирование и эксплуатационная надежность

- **Изоляция и воспроизводимость:** сборка окружения в минималистичном Docker-образе на базе `python:3.12-slim` с фиксацией версий пакетов в `requirements.txt`.
- **Ручное регрессионное тестирование FSM:** отладка сценариев отмены (`/cancel`), обработки неверных кодов, просроченных сессий и попыток повторного использования на изолированном тестовом канале.
- **Мониторинг безопасности и инцидент-менеджмент:** встроенная система мгновенных нотификаций в приватный чат администратора при попытках подбора кода, повторных запросах со скомпрометированных аккаунтов или попытках обращения к админским командам неавторизованными лицами.
